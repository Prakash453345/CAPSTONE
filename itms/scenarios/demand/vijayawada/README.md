# Vijayawada corridor demand

`vijayawada_corridor.rou.xml`: 708 vehicles over a 30-minute window (0-1800s),
generated by `build.sh` (SUMO's `randomTrips.py`, seed 42, fringe-factor 5 so
trips actually traverse the corridor end-to-end rather than all being short
local hops). Regenerate with:

```bash
export SUMO_HOME=$(python3 -c 'import sumo, os; print(os.path.dirname(sumo.__file__))')
./build.sh
```

**This is not calibrated demand.** Build guide §8.5 calls for real
turning-movement counts, OD matrix estimation, and GEH-statistic validation
against observed link counts — that's real fieldwork, done once there's a
reason to defend the numbers (M3 baselines, M4 evaluation). This is
placeholder demand whose only job is to make M1's gate demonstrable: real
vehicles moving on the real network, visible on the dashboard at 1 Hz.
`notebooks/` picks up the calibration work when M8.5 needs it.

`vijayawada_corridor.sumocfg` ties this demand to the network in
`../../networks/vijayawada/` for `sumo`/`sumo-gui`/TraCI runs.

## Vehicle mix (`assign_vtypes.py`)

`build.sh` alone produces a fleet of identical `veh_passenger` vehicles,
which is fine for M1's "traffic moves on the map" gate but wrong for M3's
person-delay metric (build guide §8.1: vehicle-delay weighted by
occupancy — a bus with 40 people must not lose to two cars). Running

```bash
python3 assign_vtypes.py
```

after `build.sh` reassigns every existing vehicle's `type=` to one of four
vTypes (car, motorcycle, auto-rickshaw, bus), by a seeded weighted draw
(seed 7), **without changing any route or depart time** — so every flow
measurement (`measure_flows.py`) and every Webster/coordination tuning
number already verified against this demand stays exactly as measured.
Each vType carries an `occupancy` param the metrics collector reads
directly:

| vType | vClass | mix share | occupancy (persons/vehicle) | `guiShape` | colour |
|---|---|---|---|---|---|
| `veh_motorcycle` | `motorcycle` | 35% | 1.3 | `motorcycle` | green |
| `veh_car` | `passenger` | 40% | 1.5 | `passenger/sedan` | cyan-blue |
| `veh_auto` | `taxi` (closest built-in class to a shared auto-rickshaw) | 20% | 2.5 | `moped` | amber |
| `veh_bus` | `bus` | 5% | 40.0 | `bus` | orange |

`guiShape` and `color` are presentational: they give the four classes a
distinct silhouette and hue in `sumo-gui`, and — via the `vehicle_type`
field the sim-service copies onto `VehiclePositionUpdated` — a distinct
marker shape in the operator console. Headless `sumo` (the sim-service
TraCI loop included) parses and ignores both, so no measured number moves.

**The mix share and occupancy figures are commonly-cited approximate
values for a mixed Indian urban arterial, not measured for this
corridor** — same honesty level as the trip generation above. vClass
physical dynamics (accel/decel/length/speed factor) are left at SUMO's
own maintained defaults for each class, not invented here; all four
classes are permitted on every lane of this network (checked against the
net.xml's `disallow` lists), so no vehicle's route changes.

The checked-in `vijayawada_corridor.rou.xml` already has this mix
applied. Re-run `assign_vtypes.py` after regenerating with `build.sh` if
you rebuild the base trips from scratch.

## Watching it in sumo-gui

```bash
sumo-gui -c vijayawada_corridor_gui.sumocfg
```

`vijayawada_corridor_gui.sumocfg` is the plain scenario plus a `<gui_only>`
block that loads `vijayawada_corridor.view.xml` — a view-settings file that
selects vehicle quality "simple shapes" and the "given vehicle/type/route
color" colour scheme, so each class shows up as its own shape and colour
instead of one uniform triangle. Non-GUI runs keep using
`vijayawada_corridor.sumocfg` (the `sumo` binary rejects `<gui_only>`).
