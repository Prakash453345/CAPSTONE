Site self-test

When a screen stays empty, the question is whether the fault is in your platform or in this page. This publishes a synthetic stream onto the real bus through the real schemas and answers operator commands the way the simulation would — so if the screens fill in, the page, the socket and api-service are all fine and the problem is in the simulation. It runs no SUMO and no control logic, it is not recorded as a run, and it produces no KPIs. Never read a number off it.

What this is

A test harness for the ITMS platform. It drives your code: the arbitration ladder, the safety interlocks, A-CA-MP, the operator-anomaly controller, the dynamic emergency router and the green corridor are all imported from itms/, not reimplemented here. Nothing inside itms/ is written to.

The short path

  1. Control room → Stack → Start bus, then Start API.
  2. Pick Light traffic and controller A-CA-MP, press Start run.
  3. Live corridor — vehicles should move within a few seconds.
  4. Anomaly injection — drop a High lane blockage and watch that edge slow down in Traffic state.
  5. Emergency response — dispatch, calculate a route, activate the corridor, watch corridor_preemption show up in Signals.
  6. KPIs & runs — run it again under Webster and compare.

If nothing starts

The Control room banner says what is missing. Almost always it is one of two things: the repo has no .venv yet (make setup in itms/), or Redis is not up (Docker Desktop not running).

Where the numbers come from

Live counters are the simulation's own ground truth, read over TraCI each tick. End-of-run KPIs are scored from SUMO's tripinfo output through the repo's control.metrics, with the same 600 s warm-up the gate scripts use. Two runs are two samples, not a result — for a defensible number use Gates.
