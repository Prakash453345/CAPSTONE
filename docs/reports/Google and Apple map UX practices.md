# Keep one map, calm the data, cite tokens

TRAFFIX already looks like Google Maps. What it lacks is the engineering and restraint that Google and Apple put behind that look. The biggest gaps are not visual. **Every route loads about 527 KiB of compressed JS, roughly 45% over the 365 KiB budget for a JS-heavy app that should be interactive in 3 s on a mid-range phone** ([infrequently.org](https://infrequently.org/2024/01/performance-inequality-gap-2024/)). **Console LCP of 4.2 s and traffic-page CLS of 0.283 both fall in Google's "poor" band** (LCP >4.0 s, CLS >0.25) ([web.dev](https://web.dev/articles/vitals)). Four pages each build their own WebGL map, where Google shares one GL context and loads its libraries on demand ([Google Maps JS API](https://developers.google.com/maps/documentation/javascript/load-maps-js-api)). On the design side, Material 3 publishes exact values for easing, duration, elevation, shape, type and components. Apple's HIG adds three rules that matter most for a data-dense operations map: use a muted basemap, show one sheet at a time, and keep translucency on floating chrome only. WCAG 2.2 adds three duties that fall directly on a live traffic map: a way to pause auto-updating data (2.2.2), non-drag pan controls (2.5.7) and 24 px targets (2.5.8). The engineering-process sources come down to a small set of rules a 1–3 person team can adopt: mini design docs, PRs of 200 lines or fewer, an 80/15/5 test mix, and a CI gate for the web app that TRAFFIX currently lacks. The sections below give the numbers and citations, each mapped to a TRAFFIX measurement, ready to paste into the audit.

## Google splits code and shares one GL context; TRAFFIX does neither

Google's performance targets are public, and they are strict. **LCP ≤2.5 s, INP ≤200 ms and CLS ≤0.1 count as "good", judged at the 75th percentile of page loads, split by mobile and desktop** ([web.dev](https://web.dev/articles/vitals)). **INP replaced FID as a Core Web Vital on 12 March 2024** ([web.dev](https://web.dev/blog/inp-cwv-march-12)). For a map dashboard, INP matters more than it looks. Each INP interaction breaks down into input delay, processing time and presentation delay. Google's fixes are to yield to the main thread with `setTimeout`, or with `requestAnimationFrame` followed by `setTimeout`, to avoid reading layout right after writing styles, and to keep the DOM small ([web.dev](https://web.dev/articles/optimize-inp)). Alex Russell's 2024 budgets make the bundle problem concrete. He measures against a Samsung Galaxy A51 at 7.2 Mbps and 94 ms RTT. On that device, **a JS-heavy app gets 365 KiB of compressed JS to be interactive in 3 s, or 650 KiB for 5 s, while a markup-centric page gets only 75 KiB** ([infrequently.org](https://infrequently.org/2024/01/performance-inequality-gap-2024/)). TRAFFIX's 540 KB fits under the 5 s budget but not the 3 s one. Its landing page, which is marketing content, carries a map library it never uses, when it should sit near the markup-centric budget.

Google's own map loader shows the pattern to copy. A small inline bootstrap defines `google.maps.importLibrary()`. Each library is fetched only when requested, and Google recommends this "dynamic import" over a script tag that loads everything ([Google Maps JS API](https://developers.google.com/maps/documentation/javascript/load-maps-js-api)). In React and Vite, the equivalent is `React.lazy` declared at module scope. Declaring it inside a component resets state on every render, and a failed load goes to the nearest Error Boundary ([react.dev](https://react.dev/reference/react/lazy)). A React Router route `lazy` that resolves its component and loader together with `Promise.all` avoids a request waterfall ([React Router](https://reactrouter.com/start/data/route-object)). Vite then preloads shared chunks in parallel and extracts each async chunk's CSS into its own file ([vite.dev](https://vite.dev/guide/features)). No source gives public bundle or Web Vitals numbers for maps.google.com itself, so there is no Google benchmark to cite. The only transferable evidence is the architecture.

That architecture includes **one rendering context**. Google's vector map, announced in 2021 as the first WebGL-accelerated web map, draws vector tiles on the client ([GMP blog](https://mapsplatform.google.com/resources/blog/using-new-webgl-powered-maps-features/), search snippet). Its WebGL Overlay View draws custom 3D content inside the basemap's own GL context, which keeps occlusion and camera sync correct ([Google](https://developers.google.com/maps/documentation/javascript/webgl/webgl-overlay-view)). **The GA release on 9 June 2022 moved to a WebGL 2 context** ([GMP blog](https://mapsplatform.google.com/resources/blog/webgl-powered-maps-features-now-generally-available/)). MapLibre supports the same discipline. `prewarm()` creates the shared web workers ahead of time and is documented for SPAs "where users navigate between different views" ([MapLibre](https://maplibre.org/maplibre-gl-js/docs/API/functions/prewarm/)). react-map-gl's `reuseMaps` keeps the Map instance and its data cache across unmount and remount; only reactive props and `initialViewState` apply on reuse ([react-map-gl](https://visgl.github.io/react-map-gl/docs/api-reference/maplibre/map)). TRAFFIX's four maps should become one map owned by a console layout route. Routes then swap sources and layers instead of rebuilding the canvas. That removes repeated style and glyph downloads, keeps the tile cache warm, and stays clear of the WebGL context cap. Split view is the exception, because it needs two viewports. It should still share `prewarm()`-ed workers, and it should dispose the second map when split view closes.

MapLibre's data path matters as much as its lifecycle. `setData` replaces a whole GeoJSON source. **`updateData` applies an incremental diff but requires a unique `id` or `promoteId` on every feature** ([MapLibre](https://maplibre.org/maplibre-gl-js/docs/API/classes/GeoJSONSource/)). Mapbox's performance guide applies to MapLibre because the two share a render path. It models render cost as roughly sources plus layers plus vertices. It recommends `setFeatureState` for hover and selection, because that "reduces layer update time by inserting runtime data without reprocessing geometries". It also recommends one large static dataset alongside one small dynamic source ([Mapbox](https://docs.mapbox.com/help/troubleshooting/mapbox-gl-js-performance/)). Three MapLibre defaults are worth changing. `fadeDuration` is 300 ms, so labels fade in on every update. `validateStyle` is true, and setting it to false in production enables tree-shaking. `canvasContextAttributes` already requests WebGL 2 at high performance ([MapLibre MapOptions](https://maplibre.org/maplibre-gl-js/docs/API/type-aliases/MapOptions/)).

The landing globe is the heaviest single asset. JPEG, WebP and AVIF all decode to raw RGBA on the GPU. By simple arithmetic, an 8192×4096 texture is about 128 MiB before mipmaps. three.js's `KTX2Loader` instead transcodes Basis Universal to whatever GPU-compressed format the device supports ([three.js](https://threejs.org/docs/#examples/en/loaders/KTX2Loader)). AVIF's savings over JPEG are real but vary widely. web.dev cites research claiming more than 50%, yet its own worked example saved only about 6% ([web.dev](https://web.dev/articles/compress-images-avif)). The globe's renderer should also be disposed when the user leaves the landing page, so it does not hold a second WebGL context next to the map. For field data, the `web-vitals/attribution` build adds about 1.5 KB brotli. It reports the INP phases, the LCP subparts and `largestShiftTarget`, the element behind the worst CLS shift ([GoogleChrome/web-vitals](https://github.com/GoogleChrome/web-vitals)). With it, the 0.283 CLS figure would come with the offending element already named.

## A list that re-sorts every second is a CLS generator by design

The traffic page's 0.283 follows directly from how CLS is defined. **CLS takes the worst "session window": shifts less than 1 s apart, capped at 5 s. Only shifts within 500 ms of a discrete input (tap, click, key) are excluded, and scrolls, drags and pinch-zooms do not count as input** ([web.dev](https://web.dev/articles/cls)). A road list that re-sorts once a second, with no user input, therefore chains every reorder into one window. Map panning cannot excuse the panel shifts it triggers, because drags don't count. The documented fixes are `transform: translate()` instead of changing layout properties, and reserved space. For long lists, `content-visibility: auto` with `contain-intrinsic-size` skips off-screen rendering; web.dev's example went from 232 ms to 30 ms. It became Baseline on 15 Sep 2025 ([web.dev](https://web.dev/articles/content-visibility)). One thing remains untested: whether a FLIP reorder done purely with transforms produces zero shift entries. It should not by spec, but TRAFFIX should confirm it with a `PerformanceObserver` rather than assume.

The stronger fix is behavioural, and control-room practice backs it. Microsoft's Real-Time Dashboards offer three relevant features. A refresh rate limit sets "a minimum time interval between refreshes". Each visual displays its last refresh timestamp, and hovering also shows when the source was last checked. A viewer-controlled pause is shown by a struck-through button ([Microsoft Learn](https://learn.microsoft.com/en-us/fabric/real-time-intelligence/dashboard-live-refresh)). WCAG backs the pause as a requirement, not a nicety. **Success criterion 2.2.2 requires a way to pause, stop, hide or throttle "any auto-updating information" shown alongside other content. Its Understanding document names "a traffic camera" as real-time content that should jump to the current state on resume rather than replay stale data** ([W3C](https://www.w3.org/WAI/WCAG22/Understanding/pause-stop-hide.html)). Nielsen's limits set the tempo. At 0.1 s a response feels instant, at 1 s flow of thought stays intact, and at 10 s attention runs out ([NN/g](https://www.nngroup.com/articles/response-times-3-important-limits/)).

The resulting spec has four parts. First, keep row order stable: sort by severity bucket, then by first-seen time, and never let a row move while the pointer or focus is inside the list. Second, collect new or re-ranked items behind an "N updates, show" pill. Third, apply a batch only on user request or at a slow cadence, with fixed row heights. Fourth, expose a "Live · updated 3 s ago" indicator. After several missed intervals it should turn into an explicit "Stale: showing data from 14:02:10" state that is visibly distinct from "No data". Grafana draws the same line, keeping No Data and Error as separate alert states ([Grafana](https://grafana.com/docs/grafana/latest/alerting/fundamentals/alert-rule-evaluation/nodata-and-error-states/), snippet only). No NN/g article codifies the "N new" pill itself. It follows from 2.2.2 and 2.4.11, not from a named pattern.

Alert volume needs a budget too. **EEMUA 191 sets a target of no more than one alarm per operator per ten minutes in normal operation, and no more than ten in the first ten minutes of a major upset** ([Seqent](https://seqent.com/blog/alarm-rationalization-explained/), a vendor summary of a paywalled standard). ISA-101's "high-performance HMI" keeps the normal state grey and saves saturated colour for abnormal conditions ([LADX](https://ladx.ai/resources/isa-101-hmi-design), snippet only). This matches the stored TRAFFIX anomaly workflow of "normal unless chained emergency". Critical events, such as a new emergency corridor, should be persistent and need acknowledgement. Auto-dismissing an actionable toast is a time limit under WCAG 2.2.1, which requires a way to turn it off, adjust it or extend it ([WCAG 2.2](https://www.w3.org/TR/WCAG22/)). Warnings can use a toast plus an inbox entry, and info can go to the log only. GOV.UK's evidence-based caution applies across all tiers: people often miss banners, and overuse makes it worse ([GOV.UK](https://design-system.service.gov.uk/components/notification-banner/)).

## WCAG 2.2 makes TRAFFIX narrate a canvas that screen readers cannot see

MapLibre gives keyboard users a start and screen-reader users nothing. **`keyboard` defaults to true. Arrow keys pan 100 px, `+`/`-` zoom one level (two with Shift), Shift+←/→ rotates 15° and Shift+↑/↓ pitches 10°** ([MapLibre KeyboardHandler](https://maplibre.org/maplibre-gl-js/docs/API/classes/KeyboardHandler/)). `reduceMotion` follows the OS preference when left unset ([MapLibre MapOptions](https://maplibre.org/maplibre-gl-js/docs/API/type-aliases/MapOptions/)). The WebGL canvas, however, exposes no features. The only plugin that turned features into focusable buttons, `mapbox-gl-accessibility`, was archived on 21 Sep 2022 ([GitHub](https://github.com/mapbox/mapbox-gl-accessibility)). Esri's SDK is the reference to copy. It gives the view `role="application"` with an accessible name and description, announces search results through live regions, traps focus in popups and returns it on close, and turns off navigation animation under `prefers-reduced-motion` ([ArcGIS](https://developers.arcgis.com/javascript/latest/accessibility/)). One caution applies: `role="application"` turns off screen-reader browse keys, so it is only safe if every map function works from the keyboard.

For TRAFFIX, the WCAG 2.2 duties translate as follows. **2.5.7 Dragging Movements (AA)** uses a map as its worked example, with "up/down/left/right buttons to move the view". It also states that keyboard equivalence alone does not pass ([W3C](https://www.w3.org/WAI/WCAG22/Understanding/dragging-movements.html)). The compass and zoom buttons therefore need on-screen pan buttons or click-to-recentre beside them. **2.5.8 Target Size (AA)** sets a 24×24 CSS px minimum. Closely spaced map pins qualify for the "Essential" exception because their position carries the meaning ([W3C](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)); the list rows that mirror those pins do not. **2.4.11 Focus Not Obscured (AA)** fails if a floating sheet, toast or legend entirely hides the focused element ([WCAG 2.2](https://www.w3.org/TR/WCAG22/)). The one-sheet rule helps, but Tab order still needs testing with the Emergency and Create Anomaly panels open. **4.1.3 Status Messages (AA)** is met with `role="status"`, `role="alert"` or `role="log"`. W3C itself warns against making an app "too 'chatty'" ([W3C](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html)). **2.3.1** caps flashing at three per second, which limits any pulsing emergency marker ([WCAG 2.2](https://www.w3.org/TR/WCAG22/)). WCAG 3 is not a reason to wait. It is still a Working Draft, last published 10 Sep 2026, with "several years of work" left ([W3C](https://www.w3.org/WAI/news/2026-09-10/wcag3/)).

The screen-reader summary needs three parts. The first is a map container labelled "Traffic map", with `aria-describedby` pointing at a text summary such as "12 corridors, 3 congested, 1 active emergency route". The second is a synchronised table or list of corridors and incidents with status in words; selecting a row flies the map to that item. That list also provides the "Equivalent" path under 2.5.8. The third is one polite live region that exists in the DOM before its first update. MDN notes that regions added dynamically need their first content deferred ([MDN](https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Guides/Live_regions)). That region should announce debounced summaries such as "3 new incidents". A separate `role="alert"`, without `aria-live`, which MDN says to omit for iOS VoiceOver, is kept for corridor activation. The WAI-ARIA feed pattern supplies the live list's mechanics. It sets `aria-busy="true"` during a batch insert and back to false afterwards, and it moves between items with Page Up/Down ([W3C APG](https://www.w3.org/WAI/ARIA/apg/patterns/feed/)). No standard fixes an announcement rate, so the debounce interval is a design choice.

Colour needs two cues, not one. **About 300 million people have colour vision deficiency, roughly 1 in 12 men.** TomTom answers this with dedicated deuteranopia, protanopia and tritanopia schemes, and with "line widths, patterns and other visual textures" ([TomTom](https://www.tomtom.com/newsroom/behind-the-map/mapping-for-color-blindness/)). WCAG 1.4.1 forbids colour as the only cue. WCAG 1.4.11 requires 3:1 contrast against adjacent colours for congestion lines, marker outlines and control icons ([WCAG 2.2](https://www.w3.org/TR/WCAG22/)). TRAFFIX should keep its green, amber and red hues but pull them apart in lightness. It should also grow line width with severity, dash closed roads, and label the legend "Free flow / Slow / Stopped / Closed". No mapping vendor publishes a validated CVD-safe congestion palette, so each pairing must be checked with a simulator. The five light-theme failures in the top bar are the same 1.4.3 and 1.4.11 problem. Passing in dark theme only shows that the light theme's tokens were never checked.

## Material 3 supplies exact numbers; Google Maps bends several of them

m3.material.io renders on the client, so every M3 value below comes from Google's generated token files. Their last update was on 6 April 2026, "update latest tokens to v34" ([material-web tokens](https://github.com/material-components/material-web/tree/main/tokens/versions/latest/sass)). The Google Maps values were measured with DevTools on google.com/maps at 1440×900 on 25 Sep 2026 ([Google Maps](https://www.google.com/maps)). They describe the live DOM on that date, not a published spec.

### Motion: two easing families, sixteen durations, six springs

| Token | Value | Use ([MDC Motion.md](https://raw.githubusercontent.com/material-components/material-components-android/master/docs/theming/Motion.md)) |
|---|---|---|
| `easing-standard` | `cubic-bezier(0.2, 0, 0, 1)` | Utility motion that starts and ends on screen |
| `easing-standard-decelerate` / `-accelerate` | `(0, 0, 0, 1)` / `(0.3, 0, 1, 1)` | Utility enter / exit |
| `easing-emphasized-decelerate` / `-accelerate` | `(0.05, 0.7, 0.1, 1)` / `(0.3, 0, 0.8, 0.15)` | M3-styled enter / exit |
| `easing-legacy` (M2) | `(0.4, 0, 0.2, 1)` | Avoid in new code |
| Durations (ms) | short 50/100/150/200; medium 250/300/350/400; long 450/500/550/600; extra-long 700/800/900/1000 | "Duration should increase as the area/traversal of an animation increases" |

These easing and duration values come from the material-web motion tokens ([_md-sys-motion.scss](https://github.com/material-components/material-web/blob/main/tokens/versions/latest/sass/_md-sys-motion.scss)). The full emphasized curve is a two-segment path that one CSS `cubic-bezier` cannot express, so the CSS token file aliases it to standard ([Motion.md](https://raw.githubusercontent.com/material-components/material-components-android/master/docs/theming/Motion.md)). Compose's bottom sheet animates with a 300 ms tween ([androidx SheetDefaults.kt](https://github.com/androidx/androidx/blob/androidx-main/compose/material3/material3/src/commonMain/kotlin/androidx/compose/material3/SheetDefaults.kt)). The Expressive springs are **fast-spatial 0.9 / 1400, default-spatial 0.9 / 700 and slow-spatial 0.9 / 300** (damping ratio / stiffness), with matching effects springs at damping 1.0 and stiffness 3800, 1600 and 800. Default-spatial is meant for partial-screen surfaces such as bottom sheets. Effects springs animate colour and opacity and "should not be overshot" ([tokens](https://github.com/material-components/material-web/blob/main/tokens/versions/latest/sass/_md-sys-motion.scss)). M3 Expressive names the bouncy scheme as its default. Its "standard" scheme has minimal bounce and suits "utilitarian applications" ([M3 blog](https://m3.material.io/blog/building-with-m3-expressive), snippet), and that is the one an operations console should choose. For framer-motion, absolute damping = ratio × 2√stiffness at mass 1, which gives about 67 for fast-spatial, 48 for default-spatial and 31 for slow-spatial. This is derived arithmetic and assumes the two libraries use comparable stiffness units.

Google Maps departs from stock M3 in the same direction each time. It is denser: a 48 px search bar, 29 px controls, and grey-based shadows built on `#3c4043` instead of dp levels. The Sign-in button's `#0b57d0` also appears to be Google's GM3 baseline blue, though that is inferred. Since TRAFFIX wants to feel like Google Maps, the measured values are the better target. Two limits still apply. First, the minimum interactive size is 48 dp in Compose ([androidx](https://github.com/androidx/androidx/blob/androidx-main/compose/material3/material3/src/commonMain/kotlin/androidx/compose/material3/InteractiveComponentSize.kt)), and Maps meets it by wrapping 32 px chips in 48 px hit areas. Second, 29 px controls pass WCAG's 24 px floor on desktop but should grow to 40–48 px on touch. Google Sans Flex was released under the OFL on 18 Nov 2025, so TRAFFIX's use of it is licensed ([Wikipedia](https://en.wikipedia.org/wiki/Product_Sans)). Maps' own UI stack uses Google Sans Text with a Roboto fallback. One piece of Google's older API guidance should not be followed: the JS API's custom-control CSS, with a 2 px radius, 40 px height and Roboto at 18 px ([Google](https://developers.google.com/maps/documentation/javascript/controls)), predates the rounded controls Maps now ships.

## Apple's contribution is restraint: muted maps, one sheet, glass only on chrome

Apple's HIG Maps page is short, and its most useful sentence is about emphasis. The **muted** style is desaturated and "great when you have information-rich content that needs to stand out against the map" ([HIG Maps](https://developer.apple.com/design/human-interface-guidelines/maps)). MapKit JS exposes it as `mapType: mutedStandard` ([MapKit JS](https://developer.apple.com/documentation/mapkitjs/map)). For TRAFFIX, this means the Google-palette OpenFreeMap basemap should have a desaturated variant for the traffic and emergency views. That lets congestion and corridor colours carry the saturation, as ISA-101 also recommends. The same page gives the rest. Cluster overlapping points. Mark selection with "an outline and color variation", not size alone. Draw overlays "above roads" by default, so labels and buildings stay visible, and "above labels" only to mask areas. Give controls contrast against the map with "a thin stroke, light drop shadow, or blend modes". Keep the selected location visible while a place card is open. Keep attribution fixed to the map with 7 pt side and 10 pt vertical padding, sitting **10 pt above the lowest resting position** of any sheet ([HIG Maps](https://developer.apple.com/design/human-interface-guidelines/maps)).

Sheets and materials confirm TRAFFIX's one-floating-sheet rule and sharpen it. The HIG says to show one sheet at a time. Resizable sheets need a grabber, which must work with VoiceOver and can be tapped to cycle detents. Medium (about half height) and large detents are standard. Nonmodal sheets let people keep working in the parent view, which is the Apple Maps model. On macOS, a **panel** suits tasks where people "repeatedly provide input and observe results" ([HIG Sheets](https://developer.apple.com/design/human-interface-guidelines/sheets)); an operator console is exactly that. Liquid Glass, announced 9 June 2025 ([Apple Newsroom](https://www.apple.com/newsroom/2025/06/apple-introduces-a-delightful-and-elegant-new-software-design/)), belongs to the controls layer only. "Don't use Liquid Glass in the content layer", and "use Liquid Glass effects sparingly". The regular variant is for text-heavy chrome. Clear glass over bright content needs a 35% dark dimming layer ([HIG Materials](https://developer.apple.com/design/human-interface-guidelines/materials)). Half sheets are inset from the display edge, and they become more opaque at full height ([Adopting Liquid Glass](https://developer.apple.com/documentation/technologyoverviews/adopting-liquid-glass)). Apple publishes no blur radii or tint opacities. Any `backdrop-filter` recipe is therefore an approximation, and it should fall back to solid fills under `prefers-contrast: more`.

Apple's motion guidance favours calm. Motion should be purposeful and brief. Avoid it on frequent interactions, let people cancel it, and never make it the only carrier of information ([HIG Motion](https://developer.apple.com/design/human-interface-guidelines/motion)). SwiftUI's presets all default to **0.5 s perceptual duration, with bounce 0 (`smooth`/default spring), 0.15 (`snappy`) and 0.3 (`bouncy`)** ([SwiftUI](https://developer.apple.com/documentation/swiftui/animation/snappy(duration:extrabounce:))). Framer Motion's `visualDuration`/`bounce` parameters map onto these directly, which is an analogy and not an Apple statement. Use bounce 0 for sheet snaps and camera moves and 0.15 for chip feedback, and skip `bouncy`. Accessibility numbers are explicit. **Hit targets are 44×44 pt by default on iOS (28 minimum) and 28×28 on macOS (20 minimum). Contrast is 4.5:1 up to 17 pt. Text must scale to 200%** ([HIG Accessibility](https://developer.apple.com/design/human-interface-guidelines/accessibility)). Reduce Motion should turn `flyTo` into `jumpTo` and replace the globe dive with a crossfade.

Two Apple assets are off-limits. **The SF font license forbids embedding and excludes mock-ups for non-Apple platforms** ([Apple Fonts](https://developer.apple.com/fonts/)). SF Symbols are licensed as system-provided images for Apple platforms ([SF Symbols](https://developer.apple.com/sf-symbols/)); the explicit ban on web use was not verified, so the safe reading is "don't". TRAFFIX should keep Google Sans Flex and an open icon set, with stroke weights matched to the text. MapKit JS is not a reasonable swap either. It needs a Developer Program membership and a JWT token, with a quota of 250,000 map views and 25,000 service calls per day ([Apple forums](https://developer.apple.com/forums/thread/127493)). It also documents no custom WebGL hook ([MapKit JS](https://developer.apple.com/documentation/mapkitjs/tileoverlay)), which would block TRAFFIX's GPU layers.

## Google's process rules scale down to a two-person team

Google's design docs are informal. They have five parts: context and scope, goals and non-goals, the design with its trade-offs, alternatives considered, and cross-cutting concerns such as security, privacy and observability. **Large projects write 10–20 pages; incremental work gets a 1–3 page "mini design doc". Skip it when the solution is obvious** ([Ubl, 2020](https://www.industrialempathy.com/posts/design-docs-at-google/)). Google's privacy team reviews design docs and code at launch ([Google Cloud](https://docs.cloud.google.com/docs/security/overview/whitepaper)). For TRAFFIX, the persistent-map refactor and the live-list redesign each deserve a mini doc. Their non-goals section, such as "no second WebGL context outside split view", does the scope control.

Code review has concrete numbers. Approve a change once it "definitely improves the overall code health", even if it is imperfect. Prefix optional comments with "Nit:". **Respond within one business day at most** ([eng-practices](https://google.github.io/eng-practices/review/reviewer/speed.html)). Size guidance differs between sources. eng-practices says "100 lines is usually a reasonable size… 1000 lines is usually too large" ([eng-practices](https://google.github.io/eng-practices/review/developer/small-cls.html)). The SWE book says about 200, and adds that most Google reviews have exactly one reviewer ([SWE book ch. 9](https://abseil.io/resources/swe-book/html/ch09.html)). Refactors go in their own change, and tests go in the same change as the logic they cover. TRAFFIX's current working tree touches 40 modified files across the web app and the Python services at once, which is the pattern these rules exist to prevent. Apple publishes no equivalent guidance.

Testing starts from test size, a separate axis from scope. **Small tests are single-process with no I/O; medium tests stay on one machine and may reach localhost only; large tests have no limit. The target mix is 80% unit, 15% integration and 5% E2E** ([SWE book ch. 11](https://abseil.io/resources/swe-book/html/ch11.html)). The popular 70/20/10 split is usually credited to the 2015 "Just Say No to More End-to-End Tests" post, but that post only asks suites to "retain that pyramid shape" ([Google Testing Blog](https://testing.googleblog.com/2015/04/just-say-no-to-more-end-to-end-tests.html)). Flakiness is treated as a first-class problem. **In 2016, 1.5% of test runs were flaky and about 16% of tests showed some flakiness. Google reports a failure only after three consecutive failures and auto-quarantines chronic offenders** ([Micco 2016](https://www.googblogs.com/flaky-tests-at-google-and-how-we-mitigate-them/)). The SWE book gives 0.15% for a similar measure, a tenfold gap the sources do not resolve. Google names browser and device tests and A/B diff regression among its larger tests ([SWE book ch. 14](https://abseil.io/resources/swe-book/html/ch14.html)). None of the sources documents Google's screenshot-diff tooling itself. For TRAFFIX, that points to Playwright `toHaveScreenshot` on the map with deterministic simulation data and the tile layer masked, plus an axe scan in both themes. That scan would have caught the light-theme failures. Under the Beyoncé Rule, accessibility and performance count as things to test ([SWE book ch. 11](https://abseil.io/resources/swe-book/html/ch11.html)), so a bundle-size budget belongs in the same CI job. No source fixes a bundle budget number for a student team. Russell's 365 KiB is the defensible starting point.

Launches follow a checklist and then a gradual rollout. Google's SRE book defines a launch as any externally visible change, and records about **70 a week**. Its checklist covers dependencies, failure modes, client behaviour (exponential backoff with jitter), capacity (launch spikes reached "up to 15 times" the estimate) and rollout planning. Feature flags expose a change to a limited group, "usually between 1 and 10 percent" ([SRE book ch. 27](https://sre.google/sre-book/reliable-product-launches/)). Canarying rules add three more constraints: run one canary at a time, watch at most about a dozen user-facing metrics, and split them by canary versus control ([SRE Workbook](https://sre.google/workbook/canarying-releases/)). Dogfooding is listed as a limited production rollout ([SWE book ch. 14](https://abseil.io/resources/swe-book/html/ch14.html)). No citable source describes Apple's internal dogfooding or HI review gates. Its public process is external betas through Feedback Assistant ([beta.apple.com](https://beta.apple.com/)) and App Store Accessibility Nutrition Labels. An app may claim a label feature only if users can finish **all common tasks** with it, and the labels will become mandatory for submissions ([App Store Connect](https://developer.apple.com/help/app-store-connect/manage-app-accessibility/overview-of-accessibility-nutrition-labels)). That "all common tasks" test is a ready-made accessibility acceptance criterion for TRAFFIX. It covers five tasks: view the map, inspect an intersection, create an anomaly, follow an emergency, and switch themes. Each must work with keyboard, screen reader, 200% text and reduced motion.

## Conclusion

The research reframes what "Google-like" means for TRAFFIX. The visible layer — palette, font, search pill, chips, compass — is already done, and it is the cheapest part of what Google and Apple do. What separates their map products is less visible. There is one map instance that outlives every view. Code loads only when a route needs it. Live data changes at a rate a person can follow and can pause. And the canvas has a text layer, because the canvas itself says nothing to a screen reader. Each of TRAFFIX's measured failures traces to one of these missing structures, not to a styling choice. That also means restyling will not move LCP, CLS or the contrast count.

The two companies also pull in different directions, and TRAFFIX should pick deliberately between them. Google's measured Maps UI is denser than Material's own spec, and M3 Expressive defaults to bounce. Apple's guidance, read with ISA-101, argues for a desaturated map, calm springs, and colour held back for abnormal states. For a traffic operations console, the Apple and control-room reading should govern behaviour: muted basemap, standard motion scheme, stable lists and an alarm budget. Google's measured values should govern dimensions and shadows. Some claims in this report rest on secondary sources: the alarm-rate figures, the WebGL context cap and the 70/20/10 test split. Those are the ones to re-check before the audit cites them as hard requirements.
